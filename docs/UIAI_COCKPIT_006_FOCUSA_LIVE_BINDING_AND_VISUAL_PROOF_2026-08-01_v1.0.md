# UIAI-COCKPIT-006 — Focusa Contract Binding, Live Projection, Functional UI, and Visual Proof

**Status:** Proposed normative amendment v1.0  
**Date:** 2026-08-01  
**Depends on:** UIAI-COCKPIT-000 through 005; Focusa Specs 137, 137A, 138, 138A, 140, 141, and 144

## 0. Constitutional law

A Focusa capability is not integrated because an endpoint exists. A Cockpit feature is not implemented because a component, route, card, schema, fixture, or design exists.

Integration requires all of the following:

1. a locked generated Focusa contract and source digest;
2. a working runtime adapter against the canonical operation;
3. actual compiled UI code rendering the capability;
4. complete loading, empty, live, stale, replaying, degraded, blocked, offline, and error states;
5. durable Focusa event or explicit freshness behavior;
6. visible state change after a real or deterministic contract-faithful event;
7. automated interaction assertions;
8. screen-capture evidence from the compiled build;
9. a SHA-bound evidence manifest;
10. release-blocking CI proof.

No item may be replaced by prose, static cards, mocks that bypass production reducers, or manually supplied screenshots.

## 2. Functional UI implementation contract

Every live Focusa surface SHALL have production UI code under `apps/cockpit/src/` and SHALL consume the same generated types, adapters, projection reducers, and event application functions used outside test mode.

Required initial surface:

```text
Focusa Live Projection Fabric
├── stream connection and replay state
├── cursor and source revision
├── Spec 137 Temporal Authority projection
├── Spec 138 Epistemic Pulse with partial-coverage truth
├── Spec 140 Agent Runtime Studio status
├── Spec 144 contract-only posture
└── real event activity rail
```

The UI SHALL remain still when no operational activity exists. Transport keepalives SHALL NOT appear as work.

## 3. Focusa stream binding

Cockpit SHALL bind to Focusa `/v1/events/health` and `/v1/events/stream`.

The client SHALL support:

- stable cursor continuation;
- `Last-Event-ID` or numeric cursor semantics;
- project and continuity filters;
- replaying, live, stale, degraded, and offline states;
- event ID and sequence deduplication;
- source-state revision display;
- bounded Activity projection;
- declared invalidation handling;
- reconnection from the last confirmed cursor.

Canonical Focusa state SHALL never be mutated in a client-local projection store.

## 4. Visual proof contract

Every release-affecting Cockpit UI capability SHALL produce automated captures from the compiled web or packaged application.

Minimum capture set for a reactive feature:

1. loading or disconnected state;
2. quiet/empty state proving no synthetic activity;
3. replaying state where applicable;
4. live state after one or more contract-faithful events;
5. blocked/degraded/error state for consequential surfaces;
6. a narrow viewport when the feature claims responsive support.

Each capture SHALL be generated by CI or an approved release-proof runner, never manually substituted.

## 6. Production reducer law

Deterministic visual fixtures MAY supply contract-faithful events, but they MUST enter through the same event parsing and state-reduction path used by the live Focusa stream. A fixture-specific renderer, hard-coded completed card, screenshot-only HTML page, or bypass around production state logic is forbidden.

At least one release gate SHALL exercise a networked Focusa-compatible HTTP and SSE source. Before a full integration claim, an approved run SHALL exercise the exact pinned Focusa daemon build.

## 7. Screen-capture acceptance

A visual proof passes only when:

- the app compiled successfully;
- the screen opened without fatal console errors;
- required selectors and text were visible;
- the expected cursor and source revision appeared after event application;
- the before and after captures have different hashes where a state transition is expected;
- no secrets or private payloads appear;
- the image dimensions meet the declared viewport;
- the capture and manifest are uploaded as immutable workflow artifacts;
- artifact absence fails CI.

## 8. Functional interaction acceptance

Screen captures complement, but do not replace, functional assertions.

Required assertions include:

- Connect invokes Focusa event health and stream surfaces;
- scope fields alter the stream query;
- event replay updates the visible cursor monotonically;
- temporal events update the temporal projection;
- prediction events update epistemic counters without claiming unavailable profiles;
- runtime-constitution events update the Runtime Studio projection;
- Spec 144 remains non-executable while runtime is implementation-open;
- disconnect closes the event source;
- malformed events cause a stale/degraded state rather than silent acceptance;
- no events results in no fake activity.

## 9. CI release gate

Cockpit CI SHALL:

1. typecheck;
2. build the static web surface;
3. start the compiled build;
4. open it in a real browser engine;
5. capture idle state;
6. apply Focusa contract-faithful replay events through production UI logic;
7. capture post-event state;
8. hash captures;
9. write the evidence manifest;
10. upload all visual proof artifacts;
11. fail if any capture or manifest is missing;
12. continue with packaged Tauri, unit, smoke, and accessibility checks.

Unit and smoke tests SHALL NOT be marked optional for an integration-conformance build.

## 10. Closure rule

A Focusa-to-Cockpit requirement remains open until code, runtime binding, event/freshness behavior, functional assertions, screen captures, evidence manifest, and CI artifact retention are all verified for the same commit.
